## Contract 1 — Secret settings (PERMANENT; amends 10a's full-replace for declared secrets only)

Declaration: `Module_Base::get_secret_settings_keys(): array` — default []. Email_SMTP returns ['password']. The controller, not modules, applies REST redaction using this declaration.

GET behavior: for each declared secret key, the payload value is replaced — '' when the stored value is empty, otherwise the literal sentinel string `__WPT_SECRET__`. Stored ciphertext or plaintext never leaves over REST. defaults member: secret keys likewise sentinel-masked if a non-empty default ever exists (today they're '').

POST behavior (sentinel resolution happens in the controller BEFORE validate_settings): if a declared secret key is absent from the body or equals `__WPT_SECRET__`, the existing stored value is spliced in unchanged (the full-replace exemption). Any other value is treated as new input and flows to validate_settings. An explicit empty string clears the secret. Type rule: a declared secret key, when present and not the sentinel, must be a string — any non-string value (null, number, array, object) is rejected with new stable code `wpt_invalid_settings`, 400, "Secret settings values must be strings." Whitespace-only strings are valid new input. Sentinel collision: a literal secret value of `__WPT_SECRET__` is unsupported by design (reserved token, means keep-existing); record in checkpoint and the method docblock.

changed semantics: computed on post-resolution encodings, so an untouched GET→POST round-trip is a clean no-op (no write, no hook).

Email_SMTP::validate_settings (this slice's secret-bearing override): storage-shape mirror of its sanitize rules — from_email sanitize_email; from_name text; smtp_host text; smtp_port absint clamped 1–65535 else 587; encryption in {none,ssl,tls} else tls; authentication/force_from bool; username text; password by IDENTITY, not by prefix: if the incoming value is string-identical to the currently stored value (the controller-spliced case) it passes through byte-unchanged; '' clears; ANY other string — including strings bearing an enc1: prefix that do not match the stored value — is new plaintext and is encrypted via the existing encrypt_password(). This closes ciphertext injection (a client cannot persist arbitrary enc1:-looking values; non-matching input is always encrypted as plaintext) and preserves no-op semantics for legacy plaintext stores (a stored legacy plaintext value under sentinel splices identically and passes through unchanged; it upgrades to enc1: only when the user submits a new password — record this legacy behavior in the checkpoint). Output contains exactly the default keys.

Content_Duplication::validate_settings (non-secret override, closes its base-floor gaps): post_types = array of sanitize_key strings filtered to registered post types (array_filter against post_type_exists), default ['post','page'] if result empty; copy_* bools; title_prefix/suffix sanitize_text_field; new_status in {draft,publish,pending,private} else draft; redirect_after in {list,edit} else list.

## Contract 2 — Action routes (PERMANENT path + permission pattern; explicit registrations, no dispatcher)

Path shape (the contract every future action inherits): `POST /wpt/v1/modules/(?P<id>[a-z0-9-]+)/actions/(?P<action>[a-z0-9-]+)` — BOTH id and action args pin the existing strict pattern `^[a-z0-9]+(?:-[a-z0-9]+)*$` with sanitize_key (no leading/trailing/double hyphens; identical to the ratified id arg). In this slice, register exactly two concrete routes against that shape; do not build a generic dispatcher (logged gap: revisit when a third action exists).

Response origins (unchanged ratified set, restated here as part of the permanent action contract): success = direct payload, NO custom envelope; handler errors = WP_Error standard shape with the stable codes below; permission failures = wpt_forbidden via the existing rest_authorization_required_code() mechanism (401 logged-out / 403 authenticated-without-cap); body-schema failures (post_id, recipient, settings) = WP-native rest_missing_callback_param / rest_invalid_param shapes, the ratified third origin — no 10b-specific validation path. canonicalized_from is a SUCCESS-payload member only, on every module-addressed route; error responses never carry it (ratify this as part of Contract 3).

Gating ladder for actions (extends the settings ladder by one rung): unknown → wpt_invalid_module 404 · pro unlicensed → wpt_pro_locked 403 · status === 'stub' (the only non-implemented value in the on-disk enum) → wpt_module_stub 400 · module NOT ACTIVE → new stable code `wpt_module_inactive`, 409, "Module is not active." (actions run module behavior; settings routes intentionally serve inactive modules, actions intentionally do not) · then action-specific flow. Aliases accepted; payload id canonical. Handlers MUST obtain the module via the existing active-instance path in Core (the loaded instance for an active module) — not load_module(), not a fresh include; if that instance is unexpectedly null despite active status, fail with the existing wpt_module_unavailable 500. The 10a zero-load exception is unchanged.

Permission pattern (two-tier, PERMANENT): permission_callback enforces the coarse capability; object-level checks live in the handler and fail with wpt_forbidden 403. No def['capability'] auto-wiring in this slice — each action declares its capability explicitly (the 10c revisit note stands).

Action A — POST /modules/content-duplication/actions/duplicate
- permission_callback: current_user_can('edit_posts'). Capability parity note (decided, recorded as inherited risk): the only object-level check is edit_post on the SOURCE, matching the existing admin_action path exactly; create/publish capability on the resulting post is not separately checked (wp_insert_post does not cap-check), and new_status comes from settings. This parity is deliberate; tightening it is a per-module-spec question, logged in checkpoint gaps.
- Body args schema: post_id, required, integer, minimum 1 (failures = WP-native shapes per the response-origins block).
- Handler: object check current_user_can('edit_post', post_id) else wpt_forbidden 403 · source must exist and not be a revision/attachment → wpt_invalid_post 404 ("Post not found.") · source post_type must be in the module's post_types setting → wpt_post_type_not_enabled 400 ("Duplication is not enabled for this post type.") · duplicate via the shared method · shared-method WP_Error (insert/copy failure) → wpt_duplicate_failed, 500, "Failed to duplicate post.", with data.reason carrying the underlying WP_Error message · response 200: { source_id, new_id, new_status, edit_link } (edit_link via get_edit_post_link(new_id,'raw')).
- Shared method (required refactor): extract the duplication body of handle_duplicate into `public function duplicate_post( int $post_id ): int|\WP_Error` honoring all settings exactly as today. The method is PURE with respect to UI: it sets no admin notices, transients, redirects, or other admin-screen state — all of that remains in handle_duplicate after delegation. handle_duplicate MUST delegate to it and maps a WP_Error return to its existing wp_die(message) behavior, byte-parity with today's insert-failure path; its nonce/cap/redirect/notice behavior is otherwise byte-unchanged. The REST handler MUST call the same method. No second duplication implementation may exist (verified by grep: wp_insert_post appears in this module only inside duplicate_post).

Action B — POST /modules/email-delivery/actions/send-test-email
- permission_callback: current_user_can('manage_wpt_email') (parity with the existing ajax handler).
- Body args schema: recipient, required, string (failures = WP-native shapes). Handler validates is_email → wpt_invalid_recipient 400 ("Please enter a valid email address.").
- Shared method (required refactor): extract the send body of ajax_send_test_email into `public function send_test_email( string $recipient ): array` with a PINNED return contract: always returns array{ sent: bool, debug: string } — never WP_Error, never throws (it wraps wp_mail, which returns bool; any internal exception or pre-send failure resolves to sent:false with whatever debug was captured, possibly ''). ajax_send_test_email MUST delegate and maps sent:false to its existing wp_send_json_error shape, byte-parity; its response contract is otherwise byte-unchanged. REST handler calls the same method. (Verified by grep: wp_mail appears in this module only inside send_test_email.)
- REST response: sent:true → 200 { sent: true, recipient, debug }. sent:false → wpt_email_send_failed, 502, "Test email could not be sent.", with data.debug carrying the capture (possibly empty). One failure code covers all send-path failures.

New stable codes from this slice (checkpoint list): wpt_module_inactive, wpt_invalid_post, wpt_post_type_not_enabled, wpt_duplicate_failed, wpt_invalid_recipient, wpt_email_send_failed, wpt_invalid_settings.

## Contract 3 — canonicalized_from parity (ratifies and closes the divergence found post-10a)

GET /wpt/v1/modules/{id} gains the top-level canonicalized_from member on alias-addressed requests, via the existing with_canonicalized_from() helper — identical placement and semantics to the settings routes. This is a deliberate additive change to a ratified payload (non-breaking; clients ignore unknown members). Convention, ratified for all current and future module-addressed routes: alias-addressed requests carry top-level canonicalized_from; canonical-addressed requests never do. The 10a decision doc's "meta" wording was an unverified inheritance from a superseded draft; this contract is the corrected, behavior-defined version.
