# Strong Password Enforcement

## 1. Metadata

- ID: `strong-passwords`
- Category: `security`
- Tier: Free
- Risk: Low
- Status: Post-Phase 1
- Replaces: Force Strong Passwords, iThemes Security (password policy only)
- Related modules: `login-security`, `session-manager`
- Default enabled: false
- Onboarding profiles: Agency, Security-First

## 2. One-Liner

Enforces configurable password strength rules per role, including minimum length, complexity requirements, and password history to prevent reuse.

## 3. Scope

Strong Password Enforcement provides:

- Configurable minimum password length.
- Toggleable complexity rules (uppercase, lowercase, number, special character).
- Per-role enforcement selection.
- Password history tracking to prevent reuse of recent passwords.
- Enforcement at all password entry points: user creation, password reset, profile update.

## 4. Things NOT To Do

- Do not reject passwords silently; always show which rule failed.
- Do not store passwords in plaintext; history entries are hashed with `wp_hash_password()`.
- Do not enforce rules on Application Passwords (they are auto-generated by WordPress core).
- Do not override `wp_check_password()` or alter authentication flow.
- Do not lock out users who have existing weak passwords; enforce only on next password change.
- Do not display password history hashes in the UI or REST API.
- Do not add a password strength meter; WordPress core already provides one.

## 5. What the User Sees

Admin settings panel under WPTransformed > Security > Strong Passwords:

- Minimum length slider (8-64, default 12).
- Checkboxes for each complexity rule.
- Role multi-select for enforcement targets.
- Password history count input.
- Toggle for enforcement on password reset emails.

On password entry (profile, reset, registration):

- Inline validation messages below the password field listing unmet rules.
- Submit button is disabled until all rules pass.
- Example message: "Password must contain at least 1 special character (!@#$%^&*)."

## 7. Hooks & Implementation

Recommended class:

```php
WPT_Strong_Passwords
```

Validation hook:

```php
add_action('user_profile_update_errors', [$this, 'validate_password'], 10, 3);
add_filter('registration_errors', [$this, 'validate_registration_password'], 10, 3);
add_action('validate_password_reset', [$this, 'validate_reset_password'], 10, 2);
```

Password history hook:

```php
add_action('profile_update', [$this, 'record_password_history'], 10, 2);
add_action('password_reset', [$this, 'record_password_history_on_reset'], 10, 2);
```

Filter for external overrides:

```php
apply_filters('wpt_strong_password_rules', $rules, $user);
apply_filters('wpt_strong_password_exempt_user', false, $user);
```

## 8. REST API

Endpoints:

```text
GET  /wp-json/wpt/v1/strong-passwords/settings
POST /wp-json/wpt/v1/strong-passwords/settings
POST /wp-json/wpt/v1/strong-passwords/validate
```

The `validate` endpoint accepts `{ "password": "...", "user_id": 0 }` and returns `{ "valid": bool, "failures": [] }`.

Permissions:

- Settings endpoints require `manage_wpt`.
- Validate endpoint requires `edit_user` for the target user, or `manage_wpt`.

## 9. Database Usage

Password history stored in user meta:

```text
meta_key: _wpt_password_history
meta_value: JSON array of { "hash": "<wp_hash>", "changed_at": "<ISO 8601>" }
```

Array is trimmed to `history_count` entries on each password change.

No custom tables required.

## 10. Exact Behavior

Validation flow:

1. User submits a new password (profile, reset, registration, or WooCommerce).
2. Module checks if user's role is in `enforced_roles`. If not, skip.
3. Check `wpt_strong_password_exempt_user` filter. If true, skip.
4. Validate minimum length.
5. Validate each enabled complexity rule via regex:
   - Uppercase: `/[A-Z]/`
   - Lowercase: `/[a-z]/`
   - Number: `/[0-9]/`
   - Special: `/[^a-zA-Z0-9\s]/`
6. If `history_count` > 0, load `_wpt_password_history` for the user. Compare new password against each stored hash using `wp_check_password()`. Reject if any match.
7. Return all failures at once (not just the first).
8. On successful password change, prepend the new password hash to history array and trim to `history_count`.

Client-side validation:

- JavaScript on profile/reset pages mirrors rules for instant feedback.
- Server-side validation is always authoritative.

## 11. Edge Cases

### WooCommerce My Account password change

Hook into `woocommerce_save_account_details_errors` to enforce rules on the WooCommerce frontend password form.

### Application Passwords

Exempt. Application Passwords are auto-generated by WordPress core and do not pass through the password entry UI. No enforcement is applied.

### wp-cli user create / user update

Hook into `wp_pre_insert_user_data` to validate passwords set via WP-CLI. CLI context is detected via `defined('WP_CLI') && WP_CLI`. Enforcement applies unless `--skip-plugins` is used (which disables the module entirely).

### Multisite user registration

Hook into `wpmu_validate_user_signup` for multisite registration flow. Enforce based on the blog's settings, not the network-level settings.

### REST API user creation

Enforce via `rest_pre_insert_user` filter when password is included in the request body.

### Bulk user import (CSV plugins)

Third-party import plugins that call `wp_insert_user()` or `wp_update_user()` will trigger validation through the standard hooks. If the import plugin bypasses hooks, enforcement cannot apply; this is documented as a known limitation.

### User has no role (e.g., removed)

If user has no role, enforcement does not apply (no role is in `enforced_roles`).

### History count set to 0

Password history checking is disabled. Existing history data is retained but not checked.

## 13. Security & Permissions

- Password history hashes are stored using `wp_hash_password()`, not reversible.
- History meta is not exposed via REST API user endpoints.
- The `validate` REST endpoint does not log or store the submitted password.
- The `validate` endpoint is rate-limited to prevent brute-force password testing (10 requests per minute per IP).
- Settings changes require `manage_wpt` capability.
- Nonce verification on all admin form submissions.

## 14. Mobile/Responsive Behavior

- Inline validation messages render below the password field and are readable at 320px viewport.
- No mobile-specific behavior; enforcement is server-side.
- WooCommerce My Account form validation respects theme-provided responsive layout.

## 15. Data Retention / Uninstall

On module deactivation:

- Settings are retained in Settings Storage.
- Password history meta keys (`_wpt_password_history`) are retained.

On plugin uninstall (if clean uninstall enabled):

- Delete all `_wpt_password_history` user meta entries.
- Remove module settings from Settings Storage.

## 16. Verification & Acceptance Criteria

- [ ] Password shorter than `min_length` is rejected on profile update.
- [ ] Missing uppercase is rejected when `require_uppercase` is true.
- [ ] Missing lowercase is rejected when `require_lowercase` is true.
- [ ] Missing number is rejected when `require_number` is true.
- [ ] Missing special character is rejected when `require_special` is true.
- [ ] All failures are returned at once, not one at a time.
- [ ] Password matching a history entry is rejected.
- [ ] Password history is trimmed to `history_count` after each change.
- [ ] User with a non-enforced role can set any password.
- [ ] Application Passwords are not validated.
- [ ] WooCommerce My Account password change is validated.
- [ ] WP-CLI `wp user create --user_pass=weak` is rejected.
- [ ] REST API user creation with weak password returns 400.
- [ ] Client-side validation shows inline errors before form submission.
- [ ] Unauthorized user cannot access settings endpoints.
- [ ] Password history hashes are not exposed in any REST response.
- [ ] Setting `history_count` to 0 disables history checking.

## 17. Deferred Features

- Breached password checking against Have I Been Pwned API (requires external HTTP call).
- Password expiration (force change after N days).
- Admin dashboard widget showing password compliance rates.
- Scheduled email reminders for users with weak passwords.

## 18. Known Gotchas

- `wp_hash_password()` uses PHPass which produces different hashes for the same input; history comparison must use `wp_check_password()` against each stored hash, not direct hash comparison.
- WordPress core's password strength meter may show "Strong" for passwords that fail module rules (e.g., long password without special character). The module's inline messages clarify which specific rules failed.
- Plugins that replace the user-edit form entirely (e.g., custom profile builders) may bypass client-side validation; server-side enforcement still applies.
- Multisite: network admins creating users on subsites should be validated against that subsite's settings, not the network admin's primary site settings.
